# 单位名称 → 全量暴露面测绘方法（低误报版）

> **适用场景**：客户只给了一个公司名 / 政府单位名，对方研发自己都不清楚有哪些系统，只能靠外部探测把暴露面摸全。
>
> **核心结论**：
> - **FOFA 只能当"候选生成器"，不能当"证据"。** 关键词命中 ≠ 是它的资产。
> - 真正靠谱的证据锚点只有几个：**ICP 备案号、SSL 证书组织名(O=)、Whois 注册人、统一社会信用代码**。这些是法定的、唯一的，误报极低。
> - 每个资产 **必须"双源交叉"** 才纳入台账，单一来源一律标"存疑"。

---

## 0. 全局思路（一张图）

```
【唯一输入】单位名称
       │
       ▼
① 锚点建立：把"名称"变成"确定的法律主体 + 主域名"
       │    （ICP备案 / 统一社会信用代码 / Whois）
       ▼
② 域名扩展：把 1 个域名变成 N 个域名
       │    （CT日志 / 被动DNS / 8种反查维度）
       ▼
③ IP 与网络：域名落地到 IP / ASN / C段 / 云存储
       │
       ▼
④ 端口与服务：谁还活着、开了什么
       │    （naabu / nmap / httpx）
       ▼
⑤ 应用层：指纹 / 前端JS / API / 历史快照 / 备份文件
       │
       ▼
⑥ 新媒体侧：公众号 / 小程序 / APP / 短链
       │
       ▼
⑦ 降误报：证据分级 + 交叉验证矩阵（本方法的灵魂）
       │
       ▼
⑧ 资产台账交付 + 复测监控
```

## 1. 阶段一：锚点建立（把"名称"变成"主体"）

> 这是整个方法的地基。锚点错了，后面全错。

### 1.1 ICP 备案查询（法定实名，第一锚点，必做）

- **平台**：工信部 `beian.miit.gov.cn`（最权威）、站长工具、爱站、天眼查"网站备案"页签。
- **用法**：
  - 用 **单位全称** 查 → 得到该主体名下**所有备案域名 + 备案号**。
  - 政府单位注意用全称："XX市XX区人民政府"、"XX市卫生健康委员会"，简称查不到。
- **要点**：
  - 一个主体往往有 **多个备案号**（网站备案、APP 备案、小程序备案分开）。
  - **备案号是最强的反查钥匙**：拿到备案号后，可以反查出同主体所有域名、以及网上所有"页面底部印了这个备案号"的站点（这一步误报极低，见 7.2）。
  - 备案主体名称 = 后面天眼查、证书查询要用的关键字。

### 1.2 政府 / 事业单位专项规则

- 党政机关网站 **必须使用 `.gov.cn`**：结构通常为「地名拼音 + 部门缩写」。
  - 例：`www.xx.gov.cn`、`zwfw.xx.gov.cn`（政务服务）、`wjw.xx.gov.cn`（卫健委）。
- 事业 / 国企单位多用 `.cn` / `.org.cn` / `.com`。
- **一定要做"同级/下级单位枚举"**：一个市局的暴露面，往往连带下属区县同名部门。
- 政务系统常有 **省市级统一政务云 / 统一平台**，域名挂在上级域名子路径下（如 `xxx.gov.cn/zwfw/`），别只看子域名。

### 1.3 天眼查 / 企查查（把主体"拆开"）

- **重点抓：统一社会信用代码**（唯一标识，拿去全网交叉用）。
- 分支机构 / 子公司 / 对外投资 → 每个都是新的"名称"，回到 1.1 再查一遍。
- 曾用名 → 老域名可能还活着，是常见遗漏点。
- 经营范围 → 推测会有哪些业务系统（如"医院"必然有 HIS/预约挂号/体检报告）。

### 1.4 Whois 注册信息（第四锚点）

- 查主域名的 **注册人组织 / 注册邮箱 / 注册时间**。
- 同一注册邮箱、同一天批量注册的域名，**大概率同一主体**。
- 注意：现在大量域名开了隐私保护，这条只能作辅助。

## 2. 阶段二：域名扩展（1 个 → N 个）

### 2.1 证书透明度日志（CT 日志）—— 高准确，优先用

- 查询：`https://crt.sh/?q=%25.主域名&output=json`
- **杀手锏：按组织名搜证书** `https://crt.sh/?O=单位全称`
  - 很多单位给员工/系统签证书时会填真实的 `O=`（组织名），直接按名称就能捞出**一堆没公开的域名**，精度远高于 FOFA。
- 同理：Censys 搜 `services.tls.certificates.leaf_data.subject.organization: "单位全称"`；Quake 用 `cert:"单位名"`。这类"证书组织名"查询误报极低。

### 2.2 被动子域名（不碰目标，先拿免费的）

- CT 日志、SecurityTrails、VirusTotal、AlienVault OTX、被动 DNS 数据集。
- 这些数据是"历史别人扫出来的"，本身不产生流量，适合第一轮。

### 2.3 主动子域名枚举

```bash
subfinder -d example.com -all -recursive -o subs_subfinder.txt
amass enum -passive -d example.com -o subs_amass.txt
# 合并去重 + 泛解析处理后再解析
cat subs_*.txt | sort -u > subs_all.txt
```

### 2.4 八种"反查维度"——把关联域名一网打尽

| 反查维度 | 怎么用 | 准确度 | 说明 |
|----------|--------|--------|------|
| **反查备案号** | 搜页面含同一备案号 | ★★★★★ | 同主体强证据 |
| **反查 IP** | 同一 IP 上的所有域名 | ★★★☆ | 共享 IP 会误伤，需再验证 |
| **反查 SSL 证书** | 同证书 / 同 O= 组织名 | ★★★★★ | 证书组织名极准 |
| **反查 Whois 注册邮箱/注册人** | ViewDNS、SecurityTrails | ★★★★ | 隐私保护则失效 |
| **反查 MX 记录** | 同邮件服务器域名 | ★★★★ | 同组织常共用邮件服务 |
| **反查 NS 记录** | 同自定义 DNS 服务器 | ★★★☆ | 自建 DNS 才有效 |
| **反查 favicon hash** | 图标哈希相同即同系统 | ★★★★ | 站群/同一套系统很好用 |
| **反查统计代码 ID** | GA/百度统计/CNZZ 的站点 ID | ★★★★★ | 同 ID = 同运营者，非常准 |

> 这 8 个维度里，**备案号、证书组织名、统计代码 ID** 三个是"几乎不会误报"的，优先用。

### 2.5 政府"站群"特征

- 很多政府网站用**统一站群 CMS**，一个主站下挂几十上百个子站。
- 表现：favicon 一致、底部备案号一致、`/module/`、`/-1/` 等相同路径。
- 抓到 1 个就能顺着站群结构批量拉出其余子站。

## 3. 阶段三：IP 与网络层资产

### 3.1 IP 归属与 ASN

```bash
# 查 ASN / 归属
whois 1.2.3.4
# 或在线：bgp.he.net、ipinfo.io
```
- 识别是否在**云厂商**（阿里云/腾讯云/华为云/AWS/政务云）→ 云上往往还有一堆没挂域名的实例。
- 同一 ASN / 同一云账号段，往往同主体。

### 3.2 C 段 / B 段探测

- 对确认归属的 IP 做 `/24`（必要时 `/16`）存活 + 端口扫描。
- 重点找"**只开端口、没挂域名**"的裸系统（后台、测试环境、管理界面）。

### 3.3 云存储桶（Bucket）

- 按单位拼音 / 缩写 / 域名去**猜桶名**，格式如：
  - 阿里云 OSS：`bucket.oss-cn-xxx.aliyuncs.com`
  - 腾讯云 COS：`bucket-125xxxx.cos.ap-xxx.myqcloud.com`
  - 华为云 OBS、AWS S3 同理。
- 云存储常泄露备份、文档、数据，是高频暴露点。

### 3.4 邮件 / 域名解析记录

- `MX` 记录 → 邮件网关厂商。
- `TXT / SPF / DMARC` 记录里常写着授权发信 IP 和第三方 SaaS 域名，能反推出在用系统。

## 4. 阶段四：端口与服务测绘

```bash
# 1) 端口扫描（快速）
naabu -l ips.txt -p - -rate 1000 -o ports.txt
# 2) 服务识别（慢但准，针对重点 IP）
nmap -sV -p- -T4 --open -iL ips.txt -oA nmap_full

# 3) HTTP 存活 + 标题 + 指纹 + 证书 + favicon（一次拿全）
httpx -l subs_all.txt -title -tech-detect -status-code -web-server \
      -favicon -jarm -o httpx_alive.txt
```

- **重点端口**：`80/443/8080/8443/8000/8888/22/3389/3306/6379/9200/27017/11211`。
- 高危端口（数据库、Redis、ES、Memcached 对外）本身就是问题。
- `httpx` 输出的 **title / tech / favicon / 证书** 直接喂给下一阶段做关联。

## 5. 阶段五：应用层暴露面

### 5.1 指纹识别

```bash
whatweb -i alive.txt --log-brief=whatweb.txt
# 或用 ehole / observer_ward 识别国产 CMS、OA、中间件
```
- 指纹用于：判断是否同一套系统（关联）、发现已知漏洞组件（风险）、识别站群。

### 5.2 前端 JS 深挖（暴露面的金矿）

```bash
# 爬取 URL（含 JS 渲染）
katana -list alive.txt -jc -d 3 -o urls.txt
# 历史 URL（Wayback / CommonCrawl / gau）
gau example.com | tee gau.txt
waybackurls example.com | tee wb.txt
```
再对 JS 文件做提取（LinkFinder / SecretFinder / 手工 grep）：
- **硬编码域名 / 子域名**（常暴露未公开系统）
- **API 路径 / 接口地址**
- **内网地址、测试地址**
- **密钥、Token、AK/SK（云凭证）**
- 第三方服务（OSS、地图、支付、短信）

### 5.3 API 接口清单

- 浏览器 F12 → Network，抓所有 XHR / Fetch。
- 搜 Swagger / OpenAPI：`/swagger-ui.html`、`/v2/api-docs`、`/api-docs`、`/openapi.json`。
- 整理成表：**URL / 方法 / 参数 / 是否鉴权 / 返回数据**。
- 无鉴权或越权接口 = 暴露面核心风险。

### 5.4 历史与备份文件

- Wayback Machine / CommonCrawl 找**已下线但曾存在**的页面和接口。
- `dirsearch / ffuf` 扫敏感路径：`.git/`、`.svn/`、`.env`、`backup.zip`、`www.zip`、`.DS_Store`、`phpinfo.php`、`actuator`。

## 6. 阶段六：新媒体 / 移动端资产

- **公众号**：搜狗微信搜索单位名 → 找到公众号 → 菜单/文章里的链接 → 反查其域名。
  - 若域名 ≠ 官网 → **当作新起点，重新走阶段二~五**。
- **小程序**：抓包得到域名，或解包 `wxapkg` 提取接口。
- **APP**：应用商店 developer 页面 → 下载 APK → 反编译提取域名/接口/密钥。
- **移动端页面在电脑上看不全**：改请求 **UA 头** 为手机/微信 UA 即可正常访问（前面已述）。
- 短链、二维码、H5 活动页 → 也可能指向独立域名。

## 7. 阶段七：降误报——证据分级与交叉验证（灵魂章节）

### 7.1 为什么 FOFA 误报高

| 误报来源 | 说明 |
|----------|------|
| 关键词匹配 title/body | 转载、引用、同名单位、新闻页都会命中 |
| 共享 IP / CDN | 同 IP 上有几百个不相关站点 |
| 证书共享 | CDN/云厂商证书覆盖海量域名 |
| 泛解析 | `*.domain` 全解析，扫出来一堆假子域 |
| 品牌词撞名 | "XX银行""XX科技"全国重名极多 |

> 所以：**FOFA 用来"找线索"，不用来"下结论"。**

### 7.2 证据分级表

| 等级 | 证据类型 | 说明 |
|------|----------|------|
| **A（法定/强）** | ICP 备案号一致 | 工信部实名，几乎零误报 |
| **A** | SSL 证书 `O=` 组织名一致 | 单位签证书时填的真实名称 |
| **A** | Whois 注册人/邮箱一致 | 需未开隐私保护 |
| **A** | 统一社会信用代码出现在页面/协议 | 强实名 |
| **B（较强）** | 页面底部"主办单位/版权"一致 | 需看具体页面 |
| **B** | 统计代码 ID（GA/百度/CNZZ）一致 | 同 ID = 同运营者 |
| **B** | favicon hash 一致 | 同套系统/站群 |
| **B** | 证书序列号/指纹一致 | 同证书复用 |
| **C（弱，需验证）** | 同 IP / 同 C 段 | 共享托管会误伤 |
| **C** | FOFA/Quake 关键词命中 | 仅线索 |
| **C** | 同 CMS / 同指纹 | 只能辅助 |

### 7.3 纳入规则（照这个判就不会错）

- **≥ 1 条 A 证据** → ✅ 确认为该单位资产，入台账。
- **≥ 2 条 B 证据** → ✅ 确认，入台账。
- **只有 B×1 或 C** → ⚠️ 标"疑似"，必须访问人工确认后再入账。
- **只有单条 C** → ❌ 标"存疑"，不进正式台账（可留观察池）。

### 7.4 交叉验证矩阵（举例）

| 候选资产 | 备案号 | 证书O= | 统计ID | favicon | 同IP | 结论 |
|----------|:---:|:---:|:---:|:---:|:---:|------|
| a.xx.gov.cn | ✅ | ✅ | — | ✅ | — | **确认** |
| test.xx.com | ✅ | — | ✅ | — | ✅ | **确认** |
| 1.2.3.4:8080 | — | — | — | — | ✅ | 疑似，需访问 |
| old.xx.net | — | — | — | — | ✅ | 存疑，不入账 |

## 8. 阶段八：资产台账与交付

### 8.1 台账字段（建议）

| 字段 | 说明 |
|------|------|
| 归属主体 | 公司/单位（含统一社会信用代码） |
| 资产地址 | 域名 / IP:端口 |
| 协议/服务 | HTTP/HTTPS/数据库等 |
| 系统名称 | 前台是什么系统 |
| 指纹 | 框架/CMS/中间件/服务器 |
| 证书信息 | O=、颁发者、到期 |
| 备案信息 | 备案号、主体 |
| **置信度** | 确认 / 疑似 / 存疑 |
| **关联证据** | 命中了哪几条 A/B/C 证据（写清楚） |
| 接口清单 | 关键 API |
| 风险点 | 未鉴权接口、弱口令、暴露数据库等 |
| 首次发现/复测时间 | 便于跟踪变化 |

### 8.2 交付材料

1. **资产台账表**（Excel/CSV，含置信度与证据列）。
2. **证据截图**（页面底部备案号、证书详情、统计 ID、whois）——每个"确认"资产至少 1 条 A 证据截图。
3. **拓扑/关系图**（主体 → 域名 → IP → 服务）。
4. **风险清单**（按暴露面严重程度排序）。
5. **复测计划**（暴露面会变，建议季度复扫）。

```
# FOFA —— 用备案号/证书，别用 title/body
body="京ICP备XXXXXXXX号"
cert="xx.gov.cn"

# Quake
cert:"单位全称"

# Censys —— 按证书组织名
services.tls.certificates.leaf_data.subject.organization: "单位全称"
```

## 10. 「15 分钟快速版」（时间紧时先做这些）

1. **工信部备案**查单位全称 → 记下所有域名 + 备案号。
2. **crt.sh 按 O=单位全称** 搜证书 → 捞隐藏域名。
3. 对主域名跑 **subfinder + httpx**（标题/指纹/favicon）。
4. **FOFA/Quake 用备案号 + 证书** 反查（不用 title）。
5. 抽样访问，**看底部备案号 / 统计 ID / 证书 O=**，按 7.3 规则判确认。
6. 出第一版台账（确认 + 疑似分开）。

> 这 6 步通常就能覆盖 70% 的暴露面，且误报极低。

## 11. 合规与注意事项

- 所有探测 **必须在书面授权的范围与时间窗口内** 进行。
- 控制扫描速率，避免影响业务；政府/关键信息基础设施目标尤其要保守。
- 发现的凭证、数据、接口漏洞 **只在授权范围内留存与报告**，不下载、不外传。
- "存疑"资产不要武断写进报告，先人工核实，避免把第三方的资产算成客户的。
